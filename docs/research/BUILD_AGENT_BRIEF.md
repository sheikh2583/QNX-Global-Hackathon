## 1. The thesis we are building evidence for

> **Trace-validated repair of scheduling bugs on a microkernel RTOS.** Kernel-event traces prove the
> root cause; precondition-guarded, OS-specific source transforms fix it; and a statistical,
> loss-aware, multi-capture oracle on the real kernel decides whether the fix is accepted.

Prior repair work (AFix PLDI'11, CFix OSDI'12, HFix, SDRacer, ESfix) fixes *correctness* concurrency
bugs and checks the fix with tests or symbolic execution. None we found repairs *priority or timing*
bugs or uses kernel-trace distributions as the acceptance oracle. That gap is the paper. Detection
alone is **not** the novelty (Côté & Dagenais 2016, Rajotte 2014 on Linux; QNX's own IDE guide shows
manual semaphore-inversion detection in System Profiler).

Research questions (use these exact labels everywhere: code, docs, tables):

| RQ | Question | Workstreams |
|---|---|---|
| **RQ1** | How reliable is the trace oracle? How often does it accept a bad patch or reject a good one, as a function of the number of captures? | R1, R2 |
| **RQ2** | Do the detectors and remedies work on real bugs in code we did not write, with the tool frozen before we saw the bugs? | R3 |
| **RQ3** | Do the safety preconditions matter? How do guarded transforms compare with naive transforms, multi-round with single-round, and (optional) LLM repair with and without trace evidence? | R5 |
| **RQ4** | Does the learned radar add anything over simple baselines, and does it transfer from generated to real bugs? | R6 |
| **RQ5** | Do the results hold on real hardware, and how much does tracing itself perturb timing? | R4 |
| **RQ6** (side) | Does the capture-as-unit gate control false alarms where the job-as-unit gate does not, and what is its power? | R8 |

## R1. A residual-rate bound for VERIFIED (Phase A, product change, quick win)

**Why:** "the bug was in 0 of 5 after-captures" bounds the remaining per-capture rate only to about
45% at 95% confidence (0 of 10: about 26%). Reviewers will compute this themselves; we should report it.

**Implement** in `src/tracelens/verdict.py`:

1. `residual_rate_upper(n_clean_after: int, k_after: int = 0, confidence: float = 0.95) -> float`:
   one-sided Clopper-Pearson upper bound. For k = 0 it is `1 - (1 - confidence) ** (1 / n)`.
   Implement the general k case with a stdlib beta-inverse (bisection on the binomial CDF is enough).
2. `runs_needed(target_rate: float, confidence: float = 0.95) -> int`: smallest n with 0 of n giving a
   bound <= target (`ceil(log(1-confidence) / log(1-target_rate))`).
3. Also report the **before-rate interval** (Clopper-Pearson two-sided) for each target kind, so the
   reader sees how reliably the bug reproduced.
4. Add per target kind to `Verdict.to_dict()`: `before_rate`, `before_rate_ci`, `after_k`, `after_n`,
   `residual_rate_upper_95`. Show one plain sentence in the terminal, SUMMARY.md and `report.html`, e.g.
   *"Not seen in 10 of 10 clean after-captures: if the bug is still there, it shows in at most 26% of
   captures (95% confidence)."*
5. **Per-period figure, descriptive only:** where a finding is per period (inversion, deadline), also
   print "0 of 2,000 periods" but label it "periods within a capture are not independent; the capture
   bound above is the claim". Never put the per-period bound in a headline.
6. Add `--confidence` (default 0.95) to `compare`, `fix`, `eval fix`.
7. Tests in `tests/test_verdict.py`: k=0 values for n = 5, 10, 20 (0.451, 0.259, 0.139 to 3 d.p.),
   a k>0 case against a precomputed value, `runs_needed(0.1) == 29`, monotonicity, and that the
   verdict category (VERIFIED/NOT FIXED/INCONCLUSIVE) is **unchanged** for every committed bundle.
8. Re-render existing bundles with `tracelens fix-report` only if no headline number changes; the bound
   is an added sentence, not a changed result. Ask the user before touching the hosted site's text.

**Done when:** tests pass, `scripts/check.sh` is green, and README "Trust rules" gains one sentence about
the bound (ask the user before editing README during Phase A).

## R2. Oracle mutation study: RQ1, the headline experiment (Phase B)

**Question:** given patches whose real effect we know, how often does the oracle say VERIFIED for a bad
patch (false accept) or NOT FIXED/INCONCLUSIVE for a good one (false reject), as N grows?

### R2.1 Mutant patches

Create `research/mutants/<workload>/<mutant_id>/` with `patch.diff`, `README.md` (what it does, why it is
good or bad) and `expected.toml` (`truth = "good" | "bad"`, `expected_verdict`, rationale). Write and commit
**all** `expected.toml` files and freeze the protocol **before capturing any mutant**.

Minimum set (add more if useful; at least 3 per workload):

| ID | Workload | Patch | Truth | Tests what |
|---|---|---|---|---|
| Z1-ref | Z1 | hand-written reference fix | good | positive control |
| Z1-noop | Z1 | comment/whitespace only | bad | trivial false accept |
| Z1-noPI | Z1 | `sem_t` → mutex **explicitly** `PTHREAD_PRIO_NONE` (QNX mutexes inherit by default, so this must be explicit) | bad | does the oracle catch inversion through a non-inheriting mutex? |
| Z1-mask | Z1 | keep the semaphore, cut the telemetry thread's work so deadlines pass while the inversion window remains | bad | symptom masking: deadline met, cause still there |
| Z1-rare | Z1 | keep the semaphore, add release offsets so the inversion occurs in ~20% of captures (use the sub-tick effect from PLAN §15) | bad | rare race: N-dependence of false accepts |
| Z1-newbug | Z1 | correct PI mutex, but logger holds it across a 3 ms flash write | bad | fix that introduces a new cause |
| Z2-ref | Z2 | reference | good | control |
| Z2-selfprio | Z2 | drop `_NTO_CHF_FIXED_PRIORITY` but the server forces its own low priority after every `MsgReceive()` | bad | fixed priority by another route |
| Z2-mask | Z2 | lower the diagnostics thread's load | bad | symptom masking |
| Z3-ref | Z3 | reference send hierarchy | good | control |
| Z3-timeout | Z3 | shorter `TimerTimeout` so the deadlock breaks faster | bad | masking a deadlock with a timeout |
| Z4-ref | Z4 | reference | good | control |
| Z4-racy | Z4 | move the **shared** copy out of the lock (a data race) | bad (functionally) | **expected false accept**: a timing oracle cannot see data races; this motivates preconditions and functional checks. Preregister it as an expected oracle failure. |
| Z4-partial | Z4 | per-worker buffers for 3 of 4 workers | bad | partial fix |
| Z5-ref | Z5 | reference | good | control |
| Z5-hist | Z5 | the historical bad remedy: worker at IST priority − 1, started after `InterruptAttachEvent()` (PLAN §15, measured to delay interrupts ~20 ms) | bad | a real past mistake of our own tool |
| Z5-unmaskonly | Z5 | unmask first but keep the work in the IST | preregister truth after reasoning it through | edge case |
| TP-ttk-ref | TTK4147 | the tool's own semaphore→PI mutex patch | good | third-party control |
| MC-ref | memcached | the one-line `recheck-before-wait` fix | good | third-party control |
| MC-wrong | memcached | signal twice instead of re-checking the flag | bad | plausible wrong fix for a lost wake-up |

### R2.2 Capture plan

- For every mutant and every positive control: **20 clean captures** of the patched build, plus 20 of the
  unpatched build (reuse the before-captures per workload). Lossy captures are replaced and counted.
- Store traces outside git (`data/research/mutants/...`); commit per-capture `analyze --json` summaries,
  SHA-256 manifests and `pidin` snapshots.
- Script: `research/mutants/run.py` builds with `qcc` (existing `fix/build.py`), captures via the
  existing capture path, resumable, logs host load.

### R2.3 Oracles to compare

Implement as pure functions in `research/oracles.py`, each taking before/after `RunSummary` lists:

| Oracle | Rule |
|---|---|
| O1 single-run | one after-capture with no target finding = accept |
| O2 deadline-only | after p99 within budget = accept (what a tester with only a stopwatch does) |
| O3 findings-only | target findings absent in all N after-captures, no statistics |
| O4 TraceLens full | `compare_runs` as shipped (findings + no new kinds + Mann-Whitney + budget) |
| O5 TraceLens + bound | O4 plus `residual_rate_upper <= 0.2` (from R1) |

### R2.4 Analysis

- For N in {1, 3, 5, 10, 20}: draw 1,000 random subsets of N after-captures (and N before-captures)
  per mutant (seeded), apply each oracle, record the verdict distribution.
- Report: **false-accept rate** (bad patches accepted), **false-reject rate** (good patches not accepted),
  **INCONCLUSIVE rate**, per oracle and per N. One table and one line plot (x = N, y = false-accept).
- Expected (write in PROTOCOL before running): O1/O2 accept Z1-mask, Z1-rare, Z2-mask often; O4 rejects
  them; Z1-rare false-accepts fall with N; Z4-racy is accepted by every timing oracle.
- Subsampled subsets overlap, so give the full-20 result as the main number and the subsampling as a
  curve, and say so.

**Reroute if the VM is unavailable:** run the same study in the simulator first (`tracelens simulate`
supports parameterised scenarios), report it as a simulator result, then repeat on the VM.

**Done when:** `docs/research/oracle_study.md` with the tables, the plot (SVG), the preregistered
expectations next to the outcomes, and `make_numbers.py` emitting every number.

## R3. Blind benchmark of real bugs in other people's code: RQ2 (step 1 in Phase A, run in Phase B)

**Why:** this is the main fix for circularity. Two real cases (TTK4147, memcached) are not a detection rate.

### R3.1 Mining (Phase A, metadata only)

Create `bench/` (top level, like `bugzoo/`) with `bench/manifest.toml`, one entry per bug:

```toml
[[bug]]
id = "memcached-1348"
project = "memcached"
url = "https://github.com/memcached/memcached/issues/1348"
buggy_commit = "..."      # upstream, exact
fixed_commit = "..."      # upstream developer fix if one exists, else ""
files_sha256 = { "logger.c" = "..." }
licence = "BSD-3-Clause"  # (verify) from the upstream LICENSE file
class_claimed_upstream = "lost wake-up at shutdown"
symptom_oracle = "driver exits 3 on hang watchdog"   # independent of TraceLens
port_layer_lines = 0
status = "candidate | reproduced | excluded"
exclusion_reason = ""
```

**Inclusion criteria** (write them into PROTOCOL.md first):
- C or C++ using POSIX threads, POSIX semaphores, condition variables, message queues, timers, or QNX APIs.
- Builds with `qcc` for QNX 8.0 with a port layer of headers/shims only; **no edits to upstream lines**.
- The bug shows up in scheduling behaviour: hang, deadlock, priority inversion, lost wake-up, starvation,
  deadline/latency regression, interrupt-handler overrun.
- Ground truth exists: an upstream issue or commit describing the bug, ideally with the developer fix.
- Licence allows redistribution, or the file is fetched by hash (as TTK4147 already does).

**Where to look** (all candidates are **(verify)**):
- The `qnx-ports` GitHub organisation: projects already ported to QNX 8.0; search their upstream
  trackers for "deadlock", "hang", "priority inversion", "lost wakeup", "missed signal", "cond_wait",
  "sem_wait", "starvation", "latency", "SCHED_FIFO".
- Middleware that runs on QNX in practice: mosquitto, nng (already started: `third_party/nng_close/`),
  ZeroMQ, libuv, Cyclone DDS / Fast DDS, ROS 2 `rcl`/`rclc` executors, PX4 uORB, lwIP's sys_arch.
- Classic concurrency bug collections, filtered to C/C++ and to scheduling-observable bugs:
  Lu et al., *Learning from Mistakes*, ASPLOS 2008 (MySQL, Apache, Mozilla, OpenOffice); RADBench
  (Jalbert, Pereira, Sen, HotPar 2011). Both **(verify)** availability.
- rt-tests history (`git log` of the upstream repository) for fixed bugs in `cyclictest`, `pi_stress`,
  `pmqtest`, `ptsematest`.
- GitHub code search for "PTHREAD_PRIO_INHERIT" commits whose message mentions inversion.

**Target:** 20–30 reproduced bugs, at least 10 of them with an upstream developer fix. Mining output is
metadata, drivers and symptom oracles only. **The person or agent who writes a driver may look at the bug;
the tool must be frozen before any driver is written** (R0 freeze tag). Write each driver so its own exit
code shows the symptom (hang watchdog, missed-deadline counter, latency histogram), independent of TraceLens.

Also add each bug's **fixed upstream version** as a negative control (false-positive check).

### R3.2 Blind run (Phase B)

1. `git tag research-freeze-1` (ask before pushing). No detector, remedy, threshold or model changes
   until the blind run is fully recorded.
2. For each reproduced bug: 10 captures buggy, 10 captures upstream-fixed; `tracelens analyze` (and
   `--radar`), then `tracelens fix` with `--runs 10`.
3. Score each bug on a rubric in `bench/RUBRIC.md` (write it before the run):
   - **D1** any HIGH+ finding on the buggy build; **D2** correct class; **D3** correct threads/objects named.
   - **F0** false positive on the upstream-fixed build (HIGH+).
   - **R1** remedy produced automatically / guidance / nothing; **R2** patch compiles; **R3** oracle VERIFIED;
     **R4** driver's own symptom gone; **R5** patch semantically equivalent to the developer fix
     (two-rater judgement: the agent proposes, the **user** confirms; record disagreements).
   - Radar: flagged buggy / flagged fixed.
4. Commit `docs/research/bench_blind.md`: one row per bug, including every miss and every false positive.

### R3.3 Post-hoc adaptation (Phase B, reported separately)

After the blind table is committed, you may add detectors/remedies for missed classes (as was done for
memcached). Report them in a **separate** table labelled "after adaptation", and evaluate each new rule
**leave-one-out**: a rule written for bug X is scored only on the other bugs, plus the zoo and the
healthy corpus for false positives. Never merge the two tables.

**Reroute if fewer than 20 bugs reproduce:** report what reproduced, add carefully documented
*re-injections* (take a real developer fix and revert it in the current upstream version) as a separate,
labelled category, and say so in THREATS.md.

## R5. Repair ablations: RQ3 (Phase B)

### R5.1 Preconditions on vs off

- Add a research-only switch (in `research/`, monkey-patching or a `--unsafe-ignore-preconditions` flag
  that is **hidden and refuses to run without `TRACELENS_RESEARCH=1`**) so each remedy applies even when
  its preconditions fail.
- Build a **precondition-violation suite** `research/precond_suite/`: small QNX C programs where the naive
  transform is wrong. At least: semaphore initialised to 0 used as a signal; wait and post in different
  functions; `sem_trywait`/`sem_timedwait` use; counting semaphore (init > 1); the fixed-priority flag
  required by a design comment and a dependent priority check; IST work that touches the device after
  the moved work; contended-lock statements that touch an aliased pointer to shared data.
- Each program has a functional test (exit code) independent of timing.
- Measure guarded vs naive across zoo + bench + suite: compile failures, functional-test failures,
  new findings, VERIFIED rate. Expected: naive breaks the suite; guarded backs off with guidance.

### R5.2 Single-round vs multi-round

Rerun the fix eval with `--max-rounds 1` vs default 3 on zoo (including the Z1 1 ms-budget variant
from the codelab) and bench. Report how many fixes need round 2+ and what the second cause was.

### R5.3 Optional LLM-repair arm (user decision required first)

Research question: *does kernel-trace evidence improve LLM repair of timing bugs?* This is timely and
publishable, but it uses an API, which the **product** deliberately does not. Rules:
- **Ask the user before starting.** If they decline, skip R5.3 and note it in THREATS.md.
- Lives only in `research/llm_repair/`, never imported by `src/tracelens/`. The user sets the API key in
  their own environment; never read, print or store it.
- Default model: the latest Claude model (`claude-opus-5-5` at the time of writing; record the exact
  model id and date in every result). Temperature/effort fixed; every request and response cached to
  disk with its hash so reruns cost nothing; hard budget cap agreed with the user.
- Three contexts per bug: (a) source only + symptom description; (b) source + TraceLens findings text;
  (c) source + findings + an evidence excerpt of the trace events cited by the findings.
- 5 samples per bug per context. Every patch goes through the **same oracle** (O4, 10 captures) and the
  same functional test. Compare with TraceLens's own remedy and the developer fix.
- Report per context: compile rate, functional pass rate, VERIFIED rate, semantic-equivalence rate.

### R5.4 Developer-fix comparison

For each bench bug with an upstream fix: is TraceLens's patch equivalent, different-but-valid, or
wrong? Rubric in `bench/RUBRIC.md`; user confirms each judgement.

## R6. Radar: honest re-evaluation, RQ4 (Phase B)

1. **Baselines**, same splits, same persistence rule, trained offline with the `[ml]` extra:
   per-feature robust-z threshold (single feature, best on validation), Isolation Forest, Local
   Outlier Factor, One-Class SVM, and a two-line hand rule ("blocked share > x and ready share > y").
   Code: `research/radar_baselines.py`.
2. **Leave-one-family-out over all families**, not only the four designed holdouts.
3. **Feature-group ablation**: drop time shares / longest intervals / priority context / IRQ masking /
   migration groups one at a time.
4. **Generator → real transfer:** score every bench bug blind (R3). Report the memcached result already
   recorded: the radar flagged the hang **and** the healthy control. This contrast (100% on the
   generator's `lost_wakeup`, useless on the real one) is a finding, not an embarrassment.
5. **False alarms per hour** on long healthy captures (≥ 1 h total): idle system, `pidin` loop,
   io-sock under network load, a bench project's healthy workload.
6. **Simulator ablation**: radar trained on real only / sim only / sim without domain randomisation /
   both. The existing "2 false alarms → 0 with sim" result becomes one row of this table.
7. Only **after** the blind run: you may try a "someone is waiting for me" feature (another thread
   joined/blocked on this one) to separate a hang from healthy parking. Report as post-hoc.

Output: `docs/research/radar_study.md`.
