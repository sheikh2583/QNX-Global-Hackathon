## 1. Thesis and research questions

*Trace-validated repair of scheduling bugs on a microkernel RTOS: kernel-event traces prove the root cause; precondition-
guarded, OS-specific source transforms fix it; a statistical, loss-aware, multi-capture oracle on the real kernel decides
whether the fix is accepted.* Prior repair work (AFix, CFix, HFix, SDRacer, ESfix) fixes correctness concurrency bugs and
checks with tests or symbolic execution; none we found repairs priority or timing bugs or uses kernel-trace distributions
as the acceptance oracle **(verify)**. Detection alone is not the novelty.

| RQ | Question | Workstreams |
|---|---|---|
| RQ1 | How reliable is the trace oracle: false accepts and rejects as a function of the number of captures? | R1, R2 |
| RQ2 | Do detectors and remedies work on real bugs in code we did not write, with the tool frozen before we saw the bugs? | R3 |
| RQ3 | Do the safety preconditions matter (guarded vs naive transforms, multi-round vs single-round, optional LLM repair with and without trace evidence)? | R5 |
| RQ4 | Does the learned radar beat simple baselines, and does it transfer from generated to real bugs? | R6 |
| RQ5 | Do results hold on real hardware, and how much does tracing perturb timing? | R4 |
| RQ6 (side) | Does the capture-as-unit gate control false alarms where job-as-unit does not, and what is its power? | R8 |

## 3. Workstreams

- **R0 Protocol and preregistration (A).** `docs/research/PROTOCOL.md` (hypothesis, expected outcome, metric, test, sample
  size, stopping and exclusion rules per experiment, written before data; each section gets a `frozen: <sha> <date>` line;
  later changes are dated amendments), `THREATS.md` (construct/internal/external/conclusion, each naming the workstream that
  addresses it or saying "not addressed"), `CLAIMS.md` (claim, evidence file, number macro, status supported/partial/
  unsupported; papers may use only "supported"), `research/README.md`. Freeze tags `research-freeze-<n>` (ask before
  pushing): record tag, `tracelens --version`, config and radar/classifier JSON SHA-256s. OSF preregistration optional.
- **R1 Residual-rate bound (A, product change).** In `verdict.py`: `residual_rate_upper` (one-sided Clopper-Pearson; for k=0
  it is `1-(1-c)^(1/n)`), `runs_needed`, a two-sided before-rate interval, per-target fields in `Verdict.to_dict()`, a plain
  sentence in the terminal, SUMMARY.md and report.html ("Not seen in 10 of 10 clean after-captures: if the bug is still there,
  it shows in at most 26% of captures (95% confidence)"), `--confidence` on compare/fix/eval fix, tests (n=5,10,20 give
  0.451, 0.259, 0.139; `runs_needed(0.1)==29`). Per-period figures are descriptive only, labelled non-independent. Do not
  edit README or the hosted site without asking.
- **R2 Oracle mutation study (B), RQ1, the headline.** `research/mutants/<workload>/<id>/` with `patch.diff`, README,
  `expected.toml` (truth good/bad, expected verdict), all committed and frozen before any capture. At least 18 mutants,
  at least 3 per workload: references as positive controls (Z1, Z2, Z3, Z4, Z5, TTK4147, memcached), no-op, PTHREAD_PRIO_NONE
  mutex (Z1), symptom-masking (Z1, Z2), rare-race via release offsets (Z1), new-cause fix (Z1), self-lowered server priority
  (Z2), shorter timeout masking a deadlock (Z3), data-race fix (Z4, **preregistered as an expected oracle failure**),
  partial fix (Z4), the historical bad IST remedy (Z5), unmask-only (Z5), signal-twice wrong fix (memcached). 20 clean
  captures per mutant and per unpatched build. Oracles in `research/oracles.py`: O1 single-run, O2 deadline-only, O3
  findings-only, O4 TraceLens full, O5 O4 plus residual bound <= 0.2. For N in {1,3,5,10,20}: 1,000 seeded random subsets;
  report false-accept, false-reject and INCONCLUSIVE rates per oracle and N; the full-20 result is the main number, the
  subsampling a curve. Reroute: run in the simulator first if the VM is unavailable.
- **R3 Blind benchmark of real bugs (mining in A, run in B), RQ2.** `bench/manifest.toml` entries (id, project, url,
  buggy/fixed commits, file hashes, licence, upstream-claimed class, symptom oracle independent of TraceLens, port-layer
  lines, status candidate/reproduced/excluded). Inclusion: C/C++ with POSIX threads/semaphores/condvars/queues/timers or QNX
  APIs; builds with qcc via headers/shims only; scheduling-observable; ground truth upstream; licence allows or fetch by hash.
  Sources to try **(verify)**: qnx-ports trackers, mosquitto, nng, ZeroMQ, libuv, Cyclone/Fast DDS, ROS 2 executors, PX4 uORB,
  lwIP, Lu et al. ASPLOS 2008, RADBench, rt-tests history. Target 20-30 reproduced, at least 10 with a developer fix; each fixed
  version is also a negative control. **Tool frozen (tag) before any driver is written.** Blind run: 10 captures buggy, 10
  fixed, analyze (+radar), fix with 10 runs; rubric in `bench/RUBRIC.md` written first (D1 any HIGH+ finding, D2 class,
  D3 threads/objects, F0 false positive on fixed, R1 remedy, R2 compiles, R3 oracle VERIFIED, R4 symptom gone, R5 equivalent to
  developer fix by two-rater judgement, radar flagged buggy/fixed). `docs/research/bench_blind.md` has one row per bug including
  every miss. After that, post-hoc rules may be added but are reported in a **separate** "after adaptation" table, scored
  leave-one-out. Reroute: re-injected real fixes reverted, labelled as a separate category.
- **R4 Hardware and probe effect (C), RQ5.** Raspberry Pi 4 with the QNX 8.0 image **(verify)**; user obtains and flashes; the
  agent writes `docs/research/HARDWARE_SETUP.md`. Reroutes: lab board, other aarch64 board, else state "no hardware". Run
